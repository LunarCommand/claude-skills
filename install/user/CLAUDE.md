## Communication style

Write plainly. Short sentences, ordinary words, no invented jargon, and no
metaphor doing work that a direct description would do better.

This is a register, not a vocabulary limit. Keep the precise technical term when
it is the right one — the goal is prose a tired reader gets on the first pass,
not prose with the precision removed. If a sentence needs a comma to survive, it
probably wants to be two sentences.

## Workflow

Follow this loop for any non-trivial change. Stop and wait at each gate.

0. **Orient** — Before planning, read the files you'll touch and any that call into them. Surface assumptions, unknowns, and anything that looks load-bearing. Ask before planning if something is ambiguous.
1. **Plan** — Align on the approach before writing code. Scale to the task: a sentence for small changes, a numbered breakdown for larger ones. The plan names the files that will change, the approach, anything explicitly out of scope, and any risks or unknowns. If you're guessing about an API, library behavior, or my intent, flag it as a guess — don't bury it as a stated fact. Gate: wait for my ack.
2. **Implement** — Write the code per the plan. Stay within the planned scope. If you discover the plan was wrong, stop and revise it with me rather than improvising. If you notice adjacent issues, list them for later — don't fix them.
3. **Test** — Run the relevant tests (unit, integration, whatever applies). Fix failures before continuing. Don't proceed past red tests without explicit say-so.
4. **Hand off for manual validation** — Stop and print a handoff to chat. Start with the heading `## Handoff` on its own line, then:

   - A **short plain-English review** — 2-4 sentences of narrative prose (not bullets): what you did and why, what you're confident about vs. uncertain, anything surprising worth flagging.
   - **Files changed** — one bullet per file.
   - **What to validate** — bullet list: files to read, commands to run, app flows to try.
   - **Noticed but didn't fix** — bullet list, or omit if nothing.

   Don't paste full diffs — I'll read them myself. **Gate: wait for my ack.**
5. **Git ops** — Once I've validated, stage and commit. Commit messages: imperative mood, no co-author or "generated by" trailers. Do not push.

   An instruction naming one step authorizes that step. "Open the PR" is not "open the PR and act on what comes back."

6. **Confirm push/release** — Ask before pushing. For projects where the next step is a release (tag, publish, deploy), ask which and wait for explicit confirmation. Default is "do nothing further."
7. **Loop** — If I don't confirm, or I come back with changes, return to step 0 with the new context. Treat each pass as a fresh planning session — don't reuse the prior plan's assumptions, file list, or test results.

   **Review findings start a new pass.** When a review returns findings — adversarial, a PR bot, or your own — report them with your proposed disposition for each, then wait. Fixing them first and presenting the finished result skips the gate however obvious the fixes look. Authorizing a review authorizes running it, not acting on what it returns.

**Never without my explicit ack**
Commit, push, amend, rebase, force-anything, touch files outside the planned scope, install dependencies, run migrations, modify config or secrets, or "clean up" code I didn't ask about. If you find adjacent issues, list them in the handoff.

## Code comments

Comments carry a maintenance cost and rot silently. Write the ones that survive.

**Default to none.** Reach for a clearer name, a smaller function, or an
extracted helper before reaching for a comment. A comment that exists to explain
what the code is doing is a signal the code should be simpler. If a block needs a
paragraph to follow, that paragraph is a bug report about the block.

**Comment the why, never the what or the how.** The code already states what it
does. Good targets: a non-obvious constraint, a rejected alternative that looks
correct, an external system's undocumented behaviour, a deliberate trade-off.

**The test is whether it describes the code as it stands.** Not how the code got
there, not what it used to do, not the reasoning that led you to write it this
way. A comment earns its place by telling a reader something true about the
current code that they cannot see from the code itself.

Length is a symptom, not the rule. Two or three lines carries most of what is
worth saying, and a comment much longer than the code it describes is usually
over-explaining. But a domain with an external specification earns more detail
than one without: where the code implements a written contract, stating the
obligation precisely is describing what the code is. Cut the unnecessary content
and the length follows. Cutting to a line count instead will take the good half.

**Do not put these in a comment:**

- *History.* "An earlier version did X", "this was reverted", "previously we".
  Git holds that. Say what is true now.
- *Figures that date.* Balances, row counts, ticket numbers, dollar amounts,
  "as of <date>" measurements. They are wrong within weeks and nobody updates
  them. Describe the shape, not the reading.
- *Narrative or self-justification.* No explaining your own past mistakes, no
  arguing with a reviewer, no "do not change this" emphasis, and no "X, not Y"
  where nobody was going to write Y. A rejected alternative earns a comment when
  a future reader would plausibly change the code to it, not when it is merely
  how you arrived at the decision. State the constraint plainly and let it
  stand.
- *Anything the README or a doc already says.* Point at it instead.

**Pointers are exempt from the length rule.** A reference to an external
authority the code must satisfy is not prose: a spec section, an RFC, a vendor
quirk's ticket, the standard a format comes from. A reader cannot recover it from
a better name or a smaller function, and it is what makes a line's obligation
traceable. Keep it to the citation and the obligation, not a summary of what the
authority says. `# §8.4.2: caller keys on every observation` earns its line;
three paragraphs explaining the section's reasoning does not, and belongs where
the long-form goes. Spec refs stay out of docstrings and live here, in this
compressed form; where a project documents its own docstring conventions — in
an `AGENTS.md` or `CONTRIBUTING.md`, say — that file governs what a docstring
may hold.

**Where the long-form belongs:** commit messages for why a change was made,
`_tasks/` for investigations and decisions, the PR description for reviewers,
the module README for operators. A file is the worst place to keep prose,
because it is the place nobody rereads when the code changes.

**Sanity check before committing:** a file that is mostly comments, or a block
that runs much longer than the code it sits above, is worth a second look. Read
it back and ask what a reader loses if it goes. Usually the answer is nothing for
most of it and something specific for two lines of it.

**A high ratio is a restructuring signal, not a deletion target.** Deleting
comments that were carrying their weight leaves worse code than the ratio you
started with, and it is the easier of the two moves, so it is the one that
happens under time pressure. If a file reads as mostly prose, the finding is
usually that the file is too big. Split it, or leave it and say why.

**Tests get one extra allowance.** A note recording why an assertion is not
vacuous, what it was mutation-tested against, or which mutant it is there to
kill, stays even at length. It is the only thing standing between a live
assertion and someone re-scoping it into a test that passes unconditionally, and
there is nowhere else it can live: a commit message does not travel with the
assertion, and a reader deleting a line does not go looking for one. Everything
else in this section applies to tests unchanged.

## Git commit messages

Always follow the 50/72 rule:

- Subject line ≤50 characters (hard cap 72), imperative mood, capitalized, no trailing period
- Blank line between subject and body
- Body wrapped at 72 characters
- Body explains *what* and *why*, not *how*
- Do NOT append the `Co-Authored-By: Claude <noreply@anthropic.com>` trailer or the `🤖 Generated with Claude Code` footer

If a commit's changes can't be summarized in ≤50 characters, prefer splitting into multiple commits over a long subject line.

## Git branches

Use a type prefix followed by a short kebab-case description. Allowed prefixes:

- `feature/` — new functionality
- `fix/` — bug fixes
- `refactor/` — code restructuring without behavior change
- `chore/` — tooling, deps, config, housekeeping
- `schema/` — database or data model changes

For ticketed work, embed the ticket ID between the prefix and description: `feature/PROJ-123-user-export`, `schema/PROJ-456-add-indexes`. Keep the descriptive portion concise (3–5 words) and lowercase.

## Pull request summaries

Write the summary as if a human authored it. Do NOT append any Claude Code attribution, including but not limited to:

- `🤖 Generated with Claude Code` (or the `:robot_face:` emoji-shortcode form)
- `Co-Authored-By: Claude` trailers
- Any "generated by", "written with", or similar AI-attribution footer

This applies to the PR description body, the title, and any comments posted as part of opening the PR.

## Releases

Releases bake docs/changelog mismatches into release notes — once a tag fires, what shipped is what the world sees. Treat the changelog as authoritative and keep it current as work lands.

Before suggesting we tag or fire a release workflow:

- **CHANGELOG must be current** — every commit since the previous release that changes user-visible behaviour should be reflected. Don't write the section once at version-bump time and assume it's final; refresh
  it as the cycle progresses, and again right before tagging.
- **Sweep the docs for stale references** — for each behaviour change in the upcoming release, grep the docs for the old wording, file paths, and flag descriptions, and reconcile. Common spots: `README`,
  `docs/USAGE`, `docs/CONFIGURATION`, `docs/ARCHITECTURE`, in-code help text.
- **Confirm the changelog date matches the day we tag** — drift is common when the entry was drafted early.
- **Read the project's release process before triggering it** — `docs/RELEASING.md` or `.github/workflows/release.yml` is authoritative. Tell me what the trigger is (tag push, GitHub Release publish, branch merge)
   before acting.
- **Hand off for a "what's about to ship" review** — show me the diff between the last release and the current main, plus the current changelog entry, and wait for an explicit ack before tagging. The general workflow's confirm-before-pushing gate (rule 6) applies; don't tag on momentum.
